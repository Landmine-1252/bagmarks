API checks updated: **2026-11-15**. Target: **1.60.1**, TOC **16001**. Source baseline: the exported Blizzard UI and generated API definitions at [Gethe/wow-ui-source commit bebcb6bf309cf41b41bd74f8ca651e6a105b2676](https://github.com/Gethe/wow-ui-source/commit/bebcb6bf309cf41b41bd74f8ca651e6a105b2676), labelled **1.60.1 (70938)**. ## Input, mail and collector compatibility

### Hover keys and settings tabs

The November 15 hover-key addition uses the same pinned Forever export. [InputDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/InputDocumentation.lua) exposes `GetMouseFoci` and `GetCursorPosition`. Blizzard's [Menu.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_Menu/Menu.lua) uses `GetMouseFoci()[1]` as the top focus. Its [EventImplementation.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_Game/Mainline/EventImplementation.lua) uses `GetCurrentKeyBoardFocus` to detect typing. BagMarks resolves only this foreground focus or its ancestors to an already registered bag button, then rereads its live GUID. It never targets through another window or falls back to a tooltip's previous owner. Hidden, unreadable, and offline items are rejected. Combined Ellesmere stacks and changed-stack review flags retain explicit selection.

`BAGMARKS_CYCLE_HOVERED` is a normal `Bindings.xml` action, separate from `BAGMARKS_TOGGLE_MODE`. Both start unbound, use the active Blizzard binding set, and refuse conflicts with normal or override bindings. The assigned key belongs to that action globally; it does not fall through to Jump away from items. Typing, capture, a carried cursor object, spell targeting, and combat suppress hover marking. No override bindings or protected click forwarding are used. The mode badge is mouse-disabled addon art beside the pointer, shown only over a readable bag item when the selected mouse gesture can mark it. It leaves the native cursor intact, follows UI scale, stops polling while marking mode is off, and hides for combat.

The native `PanelTopTabButtonTemplate` and `PanelTemplates_SetTab`/`PanelTemplates_TabResize` come from the pinned [SharedUIPanelTemplates.xml](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_SharedXML/Mainline/SharedUIPanelTemplates.xml) and [SharedUIPanelTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_SharedXML/Mainline/SharedUIPanelTemplates.lua). They apply selected-tab artwork to BagMarks' own unprotected settings frame. These source checks and offline tests establish the integration contract; keyboard routing, repeated key presses, layering, scaling, and taint still need client verification.

### Mouse, mail and minimap behavior

The optional full-size mark uses `SetAllPoints`, `SetDrawLayer`, and `SetAlpha` on BagMarks' texture. The pinned [region API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleRegionAPIDocumentation.lua) documents layer and alpha setters; the [resizing API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleScriptRegionResizingAPIDocumentation.lua) marks anchoring methods protected. Size/layer/parent changes therefore run only outside combat, using the last applied layout for combat repainting. Preferences changed during combat apply on `PLAYER_REGEN_ENABLED`.

Blizzard's pinned [shared item-button template](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_ItemButton/Shared/ItemButtonTemplate.xml) places the icon in BORDER, counts in ARTWORK, and quality borders in OVERLAY. Full-size marks use ARTWORK sublevel -1 on that button, below counts and child cooldown frames. Ellesmere's inspected renderers use ARTWORK for item images, higher frames for counts, and OVERLAY textures for borders; there the mark uses ARTWORK sublevel 1 on the base button. Its anchor follows the icon-sized overlay host, not a wide List row, and post-hooks mirror that host's visibility. Mark alpha is 0.6; native textures and scripts are not replaced. The layout metadata also detects a replaced icon target during combat and suppresses stale art. Client rendering, round-icon edges, cooldown ordering, and other skins still need an in-game pass.

Marking overlays register `AnyUp`, as used by Blizzard's compartment buttons, and pass through every unselected mouse button. New profiles and settings resets use **Ctrl + Shift + Right Click**. The configured modifier combination must match exactly: the default does not capture plain Alt, Ctrl, or Shift clicks, or Ctrl + Shift with Alt also held. Existing valid saved shortcuts, including Alt + Right Click, remain unchanged. Explicit None and Marking Mode only settings permit using a spare mouse button or a mode toggle instead. Locked-item guards are independent of the chosen marking button. The source confirms these registration methods; native hit testing with every supported mouse button still needs a client pass.

Item marks use passive textures parented to the native item button or Ellesmere's icon host, separately from the input overlays. The pinned [script-region API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleScriptRegionAPIDocumentation.lua) exposes texture visibility without the protected-frame flags present on the [frame API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleFrameAPIDocumentation.lua). In combat, existing textures can repaint while input overlays stay hidden. Creation, parenting, scaling, anchors, and mouse routing remain outside combat. A display-only slot read revalidates the live GUID and rejects unreadable data; operation reads, inventory scans, and marking remain suspended. New slots and changed icon hosts wait for combat to end. Ellesmere combined-stack icons also revalidate every cached member's GUID, count, and link, hiding uncertain groups until inventory reconciliation resumes. This establishes the implementation boundary, not a guarantee of native rendering or taint behavior; both still require in-game testing.

The mail source above focuses the recipient field when Send Mail opens and clears it on `MAIL_SEND_SUCCESS`. BagMarks post-hooks the frame's show and field's text-change scripts, then defers its fill until Blizzard's handlers finish. User-originated edits inhibit filling for the current draft, including clearing the name. Replies and nonempty fields remain unchanged. The selected default name is highlighted when the field already has focus. An unfinished edit to the default in BagMarks settings is never used. Closing the mailbox invalidates pending work, and a successful send cancels any remaining attachment queue before preparing the next draft.

Ellesmere's minimap contract was inspected at commit `1a2b149c86777860618dcd85a254097d91602e11`, using the author's [button collector](https://github.com/EllesmereGaming/EllesmereUI/blob/1a2b149c86777860618dcd85a254097d91602e11/EllesmereUIMinimap/EUI_Minimap_Buttons.lua) and [flyout implementation](https://github.com/EllesmereGaming/EllesmereUI/blob/1a2b149c86777860618dcd85a254097d91602e11/EllesmereUIMinimap/EUI_Minimap_Flyout.lua). It discovers named minimap buttons, tracks addon-intended visibility, hides grouped buttons, and reparents/resizes them for its grid. BagMarks' old repeated `SetShown(true)` calls could revive an invisible hit target, and its drag callbacks could move a collected button back toward the group toggle. Parent checks alone also missed collector rows that retain Minimap parenting.

BagMarks now changes visibility only when the user's preference changes, recognizes foreign anchors/sizes, and keeps its drag timer on a separate frame. A transparent BagMarks button disables its own mouse hit target until visible again. No Ellesmere private table, shared button, menu, layout, or callback is modified. The stable button name and icon remain discoverable. Mock regressions cover closed collectors, reparented flyouts, rows with unchanged parents, collector-owned update scripts, and an independent AddOns compartment entry. Actual behavior with the user's installed Ellesmere version remains an in-game acceptance item.

## EllesmereUI Bags integration

The reported case used EllesmereUI Bags, whose item buttons are not in Blizzard's container enumeration. In development build 1.1.1, this left the settings working while clicks and item marks had no integration with that bag UI. The missing painter registration is reproduced by an automated regression that failed before the fix.

The installed ItemLockForever 0.2.0 `UI/Badges.lua` provided the integration example. The contract was then checked against the installed EllesmereUI Bags 9.8.6 `EUI_Bags_Slots.lua`, grid/list renderers, and bank renderer. The author's [public item overlay API](https://github.com/EllesmereGaming/EllesmereUI/blob/main/EllesmereUIBags/EUI_Bags_Slots.lua) exposes `EUI_Bags.RegisterItemOverlayIcon(name, callback)` and passes `(button, data)` for live painted slots. `data` is temporary; the bank reuses it. The supported `button._textOverlay` host covers the icon, including in List view.

`Ellesmere.lua` copies only primitive slot metadata into BagMarks-owned tables, registers once when the API becomes available, and parents BagMarks overlays to that host. No addon state or replacement scripts are written onto Ellesmere buttons. `OptionalDeps` establishes load order without making Ellesmere mandatory. Creation and layout changes pause in combat. Invalid/empty placeholders, inaccessible bank slots, and stale button coordinates cannot produce a mark. The host controls clipping and visibility, so List view requires its icon column to remain visible. Offline character views are not marking targets.

Ellesmere's `_mergedCount` denotes a combined display. BagMarks groups by the same exact item link for display and menu purposes only, then asks the user to choose a physical stack. Menu actions capture the selected GUID, re-resolve it on selection, and use the ordinary per-character store. Cycle mode also opens this chooser. A group icon appears only when all known represented stacks have the same mark and their count matches the rendered total; mixed marks are described in the tooltip. The live inventory snapshot supplies summaries without adding GUID polling during idle discovery. A Locked member can guard risky group clicks, with an explicit group warning, without assigning any mark to its neighbors.

The integration uses BagMarks' own input overlays, not a replacement of `HandleModifiedItemClick` or other protected functions. Ellesmere's Quick Actions can place a separate secure spell button above a slot while Alt is held. Such actions remain outside BagMarks' click guards; users can choose another modifier or marking mode to avoid that input conflict. BagMarks also requests native item holds independently of the bag frames. Whether each quick action honors those holds requires a client test. Neither ItemLockForever nor Ellesmere files are modified. Real mouse routing, scroll clipping, and taint behavior still need the client acceptance pass.

## GUID behavior and stack policy

`GetItemGUID` identifies the physical item or stack exposed at an item location. Marks and snapshot metadata use GUID keys in per-character SavedVariables. No lookup uses an item ID to retrieve a mark. Item IDs are used only to identify potentially ambiguous stack changes and to verify an operation's captured item data.

The inspected APIs do not expose authoritative split/merge ancestry. Actual GUID stability during sort, split, merge, bank transfer, and outgoing attachment removal must be measured in Forever. The implementation therefore follows these rules:

- An ordinary move with the same GUID retains the same mark. Native holds or cursor-return guards prevent ordinary movement of Locked items; clear the mark before intentionally moving one. Movement while protection is disabled still follows the stored GUID when reenabled.
- Splitting keeps the source GUID's state; a new GUID starts Normal. There is no automatic mark inheritance.
- Merging keeps the surviving GUID's state, which may be Normal. A growing marked stack is excluded from helpers until reviewed. Possible recipients of a diminished marked stack are also flagged for review, without copying the source's state.
- Multiple possible recipients can receive a review flag. This may conservatively exclude extra stacks, but never silently marks identical copies Locked, Junk, or Mail.
- A review flag is cleared only by an explicit mark selection, including Clear Mark. The tooltip explains the required review. A menu selection deliberately marks the whole current stack.
- Snapshots are reconciled only over accessible bag IDs. Closed-bank observations and unavailable GUID marks are retained. Returning mail attachments can recover their original mark. Old GUID records may remain after sale or sending; they cannot affect a newly created GUID.
- Changes made while the addon is disabled, an inaccessible item changes GUID, or a stack loses its GUID entirely cannot be reconstructed reliably. Review those stacks manually. Settings reset intentionally does not erase marks.

The installed ItemLockForever 0.2.0 `Features/Destroy.lua`, `Holds.lua`, and `Merchant.lua` were read as examples, then the API shapes and Blizzard UI behavior were checked against the pinned export. The implementation remains standalone and only BagMarks files are changed.

The native [deletion dialogs](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_StaticPopup_Game/GameDialogDefs.lua) and [Mainline variants](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_StaticPopup_Game/Mainline/GameDialogDefs.lua) hide during their own update when the cursor is empty, except when gamepad UI is enabled. Returning the cursor therefore lets the ordinary mouse dialog dismiss itself, whichever event handler runs first. BagMarks does not alter these dialogs, their accept callbacks, or deletion functions. Some accept callbacks can delete by GUID without a cursor, so returning the cursor alone cannot guarantee those paths are safe.

Blizzard uses `C_Item.LockItem` and GUID unlocks for temporary auction and runeforge selections. BagMarks requests holds only during transfer or item-targeting contexts, independently of use-spell classification. It checks the exact location/GUID, skips preexisting busy/held items, records ownership before synchronous lock events, and confirms an acquired hold. Only recorded acquisitions are released when a context ends, the mark changes, protection is disabled, or the player logs out. Saved marks remain while ordinary use, equipping, sorting, and bank movement stay available. The client exposes no lock-owner token. If another addon acquires the same hold later, ownership cannot be perfectly distinguished. Simultaneous lock addons require testing and may conflict.

The release-verification patch pairs `LockItem(location)` with `UnlockItem(location)` when the current location resolves to the recorded GUID, as Blizzard's [auction item display](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_AuctionHouseUI/Shared/Blizzard_AuctionHouseSharedTemplates.lua) does. The pinned item API declares this method without a protected/combat restriction. Missing or thrown location unlocks fall back to `UnlockItemByGUID` for the owned GUID. A successful `pcall` is not an acknowledgement: the acquisition record remains until an exact readable location reports `IsLocked == false`. Delayed verification observes for up to two seconds without sending further unlock requests, then retains an unverified status and warns once. Later events can still confirm release. A new acquisition invalidates the old check token. Unreadable data never proves release, and a preexisting busy item is never acquired or unlocked. The busy flag also covers server item movement, so retaining the record does not prove an addon lock still exists. A release already forgotten by an earlier build cannot be safely reconstructed from an item ID or mark.

Transfer/targeting protection updates synchronously on context events. The pinned spell-book export declares `CURRENT_SPELL_CAST_CHANGED` synchronous. Either positive `SpellCanTargetItem()` or `SpellCanTargetItemID()` result applies a hold; if those are unavailable, a positive `SpellIsTargeting()` result is the fallback. Unknown optional targeting data does not freeze every Locked item. Ground targeting alone does not hold an item supplying its own spell. Merchant, mail, trade, and auction events acquire holds before deferred UI work. Closing the final risk releases owned holds for all item types. Banking alone is not a risk context. Direct or unreadable spell-targeting paths retain the documented protection limits.

Only an explicit, readable `false` clears stale mailbox state. A hide notification gets a next-frame recheck if the client state has not settled. While the mail flag remains set, a throttled query also handles missed notifications, including in combat; it stops once closed. Cleanup invalidates recipient callbacks, cancels attachment work, and rechecks owned holds. Other active risks and non-reusable locks remain effective. Hidden UI alone never proves that mailing has ended. Missing, throwing, or secret queries retain protection and rely on ordinary close events.

Tooltip processing also rechecks an earlier owned hold outside transfer/targeting contexts, before the label-preference gate. This can release a hold created under the previous permanent-hold policy. Use-spell and consumable metadata are never required for ordinary gameplay. The check does not acquire ownership of a foreign hold, change the saved mark, forward a click, or bypass GUID/context validation.

`Diagnostics.lua` is an on-demand reader, separate from these repairs. `/bm debug` and `/bmcheck` populate a copyable native `UIPanelInputScrollFrameTemplate` edit box, defined in the pinned [scroll templates](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_SharedXML/SecureScrollTemplates.xml). The hidden report window is created at initialization. Reports do not call protection refresh, unlock, transfer, or SavedVariables mutation functions. Combat reports omit inventory scans; missing and secret values are labelled unknown. Filters use item IDs only to choose report entries; each entry's state and ownership still come from its exact live GUID. Native scrolling, focus, clipboard copying, and taint need client verification.

The pinned [cursor export](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/CursorDocumentation.lua) marks the event synchronous. Merchant recovery uses the native [buyback UI APIs](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/MerchantFrame.lua), including the third return from `GetBuybackItemInfo` as the price. It snapshots existing GUIDs on opening/enabling, excludes historical entries, rechecks identity and funds immediately before `BuybackItem`, and verifies the same GUID returned to an item location. Each request waits at most two seconds and is never retried while that entry remains. Calls are serialized; a timeout or thrown purchase error stops automatic recovery for that merchant visit so a late response cannot invalidate another request's index. Missing identity prevents recovery; rejected or unverified returns produce a warning. Closing the merchant, disabling BagMarks, or logout invalidates pending work. Recovery pauses during combat.

Mail handling conservatively excludes bound and account-bound items even if a specific recipient would be eligible. The client remains the final authority for unique, duration, conjured, level, faction, and realm restrictions. Refused attachments are returned from the cursor picked up by that action, the queue stops, and the marks remain. A two-second acknowledgement timeout never retries a destructive operation automatically.

## Automatic marked-junk sales

Automatic selling is an explicit, account-wide preference, disabled by default. It uses the existing `MERCHANT_SHOW`, `C_Timer.After`, and `C_Container.UseContainerItem` APIs, with no new API dependencies. The pinned container documentation above exposes this function without a hardware-event restriction annotation. Native event-driven sale behavior still needs a Forever test; the addon does not bypass restrictions if a call fails.

Only a transition into an open merchant schedules a sale. A short deferred start lets native merchant setup finish, then captures eligible carried Junk GUIDs. Later marks and inventory updates do not expand that selection or restart a stopped sale. Enabling the option at an already-open merchant takes effect on the next visit. A deliberate manual preview cancels the delayed automatic start; an existing BagMarks confirmation also prevents background selling.

Automatic and manual sales share eligibility and per-action revalidation of GUID, mark, count, and price. The merchant's Buy tab must be visible, the cursor empty, and item targeting and combat inactive. Queues wait for each result and stop on rejection or the existing two-second timeout. Turning the preference off cancels automatic work while leaving an explicitly confirmed manual sale alone. Merchant closure, combat, reset, disable, and logout invalidate queued callbacks. The automatic queue handles all captured eligible stacks; manual previews retain their 12-stack cap. The merchant's finite buyback capacity still applies.
