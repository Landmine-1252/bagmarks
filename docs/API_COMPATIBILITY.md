```sh
python3 tools/audit_api.py /path/to/wow-ui-source
```

The addon checks required namespaces and method availability. It does not use an interface-number threshold to infer a Classic API. Missing item identity disables item features; missing optional menu or settings support does not substitute a legacy implementation. Unreadable or secret item data is ignored before comparison. Events are registered defensively for differing client revisions.

## Input, mail and collector compatibility

### Hover keys and settings tabs

The November 15 hover-key addition uses the same pinned Forever export. [InputDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/InputDocumentation.lua) exposes `GetMouseFoci` and `GetCursorPosition`. Blizzard's [Menu.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_Menu/Menu.lua) uses `GetMouseFoci()[1]` as the top focus. Its [EventImplementation.lua](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_Game/Mainline/EventImplementation.lua) uses `GetCurrentKeyBoardFocus` to detect typing. BagMarks resolves only this foreground focus or its ancestors to an already registered bag button, then rereads its live GUID. It never targets through another window or falls back to a tooltip's previous owner. Hidden, unreadable, and offline items are rejected. Combined Ellesmere stacks and changed-stack review flags retain explicit selection.

`BAGMARKS_CYCLE_HOVERED` is a normal `Bindings.xml` action, separate from `BAGMARKS_TOGGLE_MODE`. Both start unbound, use the active Blizzard binding set, and refuse conflicts with normal or override bindings. The assigned key belongs to that action globally; it does not fall through to Jump away from items. Typing, capture, a carried cursor object, spell targeting, and combat suppress hover marking. No override bindings or protected click forwarding are used. The mode badge is mouse-disabled addon art beside the pointer, shown only over a readable bag item when the selected mouse gesture can mark it. It leaves the native cursor intact, follows UI scale, stops polling while marking mode is off, and hides for combat.

BagMarks creates its sidebar and dialogs from native, unprotected frames, buttons, edit boxes and font strings. The client supplies the text metrics and keyboard focus. Its menu compositor supplies the temporary textures for the themed marks beside bag menu actions. [Backdrop template](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_SharedXML/Backdrop.xml) [Blizzard menu implementation guide](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_Menu/11_0_0_MenuImplementationGuide.lua#L264-L300)

### Mouse, mail and minimap behavior

The optional full-size mark uses `SetAllPoints`, `SetDrawLayer`, and `SetAlpha` on BagMarks' texture. The pinned [region API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleRegionAPIDocumentation.lua) documents layer and alpha setters; the [resizing API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleScriptRegionResizingAPIDocumentation.lua) marks anchoring methods protected. Size/layer/parent changes therefore run only outside combat, using the last applied layout for combat repainting. Preferences changed during combat apply on `PLAYER_REGEN_ENABLED`.

Medium and full marks use ARTWORK sublevel -1 on Blizzard item buttons, below counts and child cooldown frames. Ellesmere places its count on a higher frame and uses ARTWORK for item images, so BagMarks uses ARTWORK sublevel 1 on the base button. Both marks follow the icon host's size and visibility in list view. Medium uses an opaque corner mark and full uses 0.6 alpha across the icon. [Shared item-button template](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_ItemButton/Shared/ItemButtonTemplate.xml)

Marking overlays register `AnyUp`, as used by Blizzard's compartment buttons, and pass through every unselected mouse button. New profiles and settings resets use **Ctrl + Shift + Right Click**. The configured modifier combination must match exactly: the default does not capture plain Alt, Ctrl, or Shift clicks, or Ctrl + Shift with Alt also held. Existing valid saved shortcuts, including Alt + Right Click, remain unchanged. Explicit None and Marking Mode only settings permit using a spare mouse button or a mode toggle instead. Locked-item guards are independent of the chosen marking button. The source confirms these registration methods; native hit testing with every supported mouse button still needs a client pass.

In combat, existing mark textures repaint from readable GUIDs. New textures and changes to their layout wait until combat ends. BagMarks configures a separate click receiver for each supported mouse button outside combat. When the configured chord is held, it positions the matching receiver over the foreground bag slot and rechecks the slot when clicked. Other buttons pass through. Explicit mark actions can read live items, including the individual stacks in an Ellesmere group. Background inventory reconciliation, sales and draft preparation resume after combat. Native hit testing and taint still need a client pass. [Forever frame input API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleScriptRegionAPIDocumentation.lua)

Blizzard focuses the recipient when showing Send Mail, sets reply mode after showing the tab, and resets the form on `MAIL_SEND_SUCCESS`. BagMarks waits until the next frame, then fills an empty To field once per fresh draft. A player edit or an existing name takes precedence. The default is selected if To already has focus. Hiding the tab cancels the attachment queue. A confirmed send of a completed, addressed batch can start the next letter when automatic attachment is enabled. [Forever mail frame source](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_MailFrame/MailFrame.lua)

Mail routing uses the numeric class and subclass from `C_Item.GetItemInfoInstant`. The supported Tradegoods subclasses are Cloth (5), Leather (6), Metal & Stone (7), Cooking (8) and Herb (9). An unreadable classification defers a stack that needs a class-based rule. Cooking also recognizes the 37 ingredients for Forever meals and drinks filed outside subclass 8. A configured material destination takes priority for shared ingredients. [Forever item API](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua#L659) [Build 1.60.1.70959 item classes](https://wago.tools/db2/Item?build=1.60.1.70959) [Cooking recipe reagents](https://sktools.gg/forever/professions/cooking)

Within the Recipe class, BagMarks uses the profession subclass. Six gathering blueprints use the generic Book subclass, six blacksmithing plans use Leatherworking, and two leatherworking patterns use Tailoring in build 1.60.1.70959. BagMarks identifies those teaching items by ID. Other generic books take the usual fallback. [Forever recipe subclasses](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemConstantsDocumentation.lua#L521-L539) [Profession teaching items](https://sktools.gg/forever/professions)

The Mage scroll category matches the 17 untranslated item IDs in Forever build 1.60.1.70959. This keeps power-up scrolls with their usual recipients even when both kinds have the same consumable subclass. Player-defined item IDs take priority. [Forever Comprehension item data](https://sktools.gg/forever/professions/comprehension)

On Forever, BagMarks reads the player's first name and surname from the native unit name functions. When the unit token returns an incomplete name, it also checks the player's GUID. A complete regional name is sufficient for mail while the realm is loading. A fresh draft waits for a complete name before applying its recipient and attaching items. Schema 8 also repairs previous `First-Surname` roster keys and matching saved destinations, including per-character overrides loaded on later logins. [Forever name formatter](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_FrameXMLUtil/Camelot/NameUtil.lua#L14-L29) [Blizzard's character naming guide](https://news.blizzard.com/en-us/article/24304161/create-a-name-of-your-own-in-wow-forever)

Opening the visible Send Mail tab can start one automatic batch per draft. The button uses the same queue. Each attachment requires its expected item ID and count, plus the exact tooltip GUID when available. If the tooltip lacks a GUID, the queue also verifies that the marked GUID left the bags. BagMarks checks the first occupied slot after attachment updates and queue acknowledgements. A blank subject gets the item name and stack count, or a provisional title while item data loads. Blizzard uses `SendMailFrame.previousItem` to update or clear an auto-generated title when attachments change. [Forever subject handling](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_MailFrame/MailFrame.lua#L1285-L1337)

Ellesmere's minimap contract was inspected at commit `1a2b149c86777860618dcd85a254097d91602e11`, using the author's [button collector](https://github.com/EllesmereGaming/EllesmereUI/blob/1a2b149c86777860618dcd85a254097d91602e11/EllesmereUIMinimap/EUI_Minimap_Buttons.lua) and [flyout implementation](https://github.com/EllesmereGaming/EllesmereUI/blob/1a2b149c86777860618dcd85a254097d91602e11/EllesmereUIMinimap/EUI_Minimap_Flyout.lua). It discovers named minimap buttons, tracks addon-intended visibility, hides grouped buttons, and reparents/resizes them for its grid. BagMarks' old repeated `SetShown(true)` calls could revive an invisible hit target, and its drag callbacks could move a collected button back toward the group toggle. Parent checks alone also missed collector rows that retain Minimap parenting.

BagMarks now changes visibility only when the user's preference changes, recognizes foreign anchors/sizes, and keeps its drag timer on a separate frame. A transparent BagMarks button disables its own mouse hit target until visible again. No Ellesmere private table, shared button, menu, layout, or callback is modified. The stable button name and icon remain discoverable. Mock regressions cover closed collectors, reparented flyouts, rows with unchanged parents, collector-owned update scripts, and an independent AddOns compartment entry. Actual behavior with the user's installed Ellesmere version remains an in-game acceptance item.

## EllesmereUI Bags integration

The reported case used EllesmereUI Bags, whose item buttons are not in Blizzard's container enumeration. In development build 1.1.1, this left the settings working while clicks and item marks had no integration with that bag UI. The missing painter registration is reproduced by an automated regression that failed before the fix.

The installed ItemLockForever 0.2.0 `UI/Badges.lua` provided the integration example. The contract was then checked against the installed EllesmereUI Bags 9.8.6 `EUI_Bags_Slots.lua`, grid/list renderers, and bank renderer. The author's [public item overlay API](https://github.com/EllesmereGaming/EllesmereUI/blob/main/EllesmereUIBags/EUI_Bags_Slots.lua) exposes `EUI_Bags.RegisterItemOverlayIcon(name, callback)` and passes `(button, data)` for live painted slots. `data` is temporary; the bank reuses it. The supported `button._textOverlay` host covers the icon, including in List view.

`Ellesmere.lua` copies only primitive slot metadata into BagMarks-owned tables, registers once when the API becomes available, and parents BagMarks overlays to that host. No addon state or replacement scripts are written onto Ellesmere buttons. `OptionalDeps` establishes load order without making Ellesmere mandatory. New mark textures and changes to icon layout wait until combat ends. Invalid/empty placeholders, inaccessible bank slots, and stale button coordinates cannot produce a mark. The host controls clipping and visibility, so List view requires its icon column to remain visible. Offline character views are not marking targets.

Ellesmere's `_mergedCount` denotes a combined display. BagMarks groups by the same exact item link for display and menu purposes only, then asks the user to choose a physical stack. Menu actions capture the selected GUID, re-resolve it on selection, and use the ordinary per-character store. Cycle mode also opens this chooser. A group icon appears only when all known represented stacks have the same mark and their count matches the rendered total; mixed marks are described in the tooltip. The live inventory snapshot supplies summaries without adding GUID polling during idle discovery. A Locked member can guard risky group clicks, with an explicit group warning, without assigning any mark to its neighbors.

The integration uses BagMarks' own input overlays, not a replacement of `HandleModifiedItemClick` or other protected functions. Ellesmere's Quick Actions can place a separate secure spell button above a slot while Alt is held. Such actions remain outside BagMarks' click guards; users can choose another modifier or marking mode to avoid that input conflict. BagMarks also requests native item holds independently of the bag frames. Whether each quick action honors those holds requires a client test. Neither ItemLockForever nor Ellesmere files are modified. Real mouse routing, scroll clipping, and taint behavior still need the client acceptance pass.

## GUID behavior and stack policy

`GetItemGUID` identifies each physical stack. Its mark follows that GUID through sorting, banking and attachment removal. Every sale and attachment rechecks the live GUID. Schema 5 keeps the sender override, individual marks and remembered Mail or Junk item IDs in `BagMarksCharDB`. WoW loads that table for the current character. A mailed stack with the same GUID on another character is classified from the receiving character's save.

The switches for remembering items, auto-attaching mail and filling the To field are account preferences. On upgrade, a former account-wide recipient is available through **Use previous recipient** in Mail. Claiming it writes the name to the current character and removes the old account suggestion. Shared material routes, the bank alt and realm-qualified character names recorded at login live in `BagMarksDB`. A material route takes priority over the sender override and the account bank alt.

- With remembering enabled, an explicit Mail or Junk choice teaches a rule. Clear Mark removes the rule. A Locked choice protects only that copy. The store records the copies already in the bags before teaching a rule.
- The store applies a remembered mark when a readable stack arrives in carried bags, a stack gains units or an item is withdrawn from the bank. It preserves the mark on any copy the player already classified. Disabling the option pauses learning and application. Resetting settings pauses it and retains the rules.
- The client supplies counts and GUIDs without split or merge ancestry. By default a split child starts Normal and a growing marked stack needs review. A type rule permits growth or a split when observed source marks agree with it. A shrinking Locked, oppositely marked or review-pending stack can put potential recipients into review. Only an explicit mark selection clears that flag.
- Inventory scans preserve observations for inaccessible bank bags. A rule requires a readable GUID before creating a mark. The seller and mail queue still apply their own binding, quest, refund and busy checks. Actual GUID stability across server transfers requires in-game verification.

## Scope of lock protection

The protection layer is implemented in `Protection.lua`. The installed ItemLockForever 0.2.0 `Features/Destroy.lua`, `Holds.lua`, and `Merchant.lua` were read as examples, then the API shapes and Blizzard UI behavior were checked against the pinned export. The implementation remains standalone and only BagMarks files are changed.

| Action | Implemented behavior | Remaining limit |
| --- | --- | --- |
| BagMarks bulk sale or attachment | Requires the exact Junk/Mail state and a reviewed, readable, eligible GUID before each action. | Runtime API eligibility and server timing still need verification. |
| Selling, transferring, and item targeting | Request a native hold on exact Locked GUIDs while merchant, mail, trade, auction, or item-targeting actions are active. Opening the bank alone does not hold items. | Native right-clicks in these contexts can transfer or sell items, so use/equip may also be blocked until they close. Holds do not establish a server-side veto; unreadable identity and event gaps remain. |

Native right-click equip/use and dragged equipping remain available. Consumables can be consumed intentionally. GUID marks persist while equipped and reappear when items return to bags. No item-use or equip API is called to forward a click. | Native game restrictions, cooldowns, foreign holds, and unavailable client data can still prevent an action. Equipment-panel icons are outside the bag-overlay scope. |

A mismatching readable cursor is left alone. The native [deletion dialogs](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_StaticPopup_Game/GameDialogDefs.lua) and [Mainline variants](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_StaticPopup_Game/Mainline/GameDialogDefs.lua) hide during their own update when the cursor is empty, except when gamepad UI is enabled. Returning the cursor therefore lets the ordinary mouse dialog dismiss itself, whichever event handler runs first. BagMarks does not alter these dialogs, their accept callbacks, or deletion functions. Some accept callbacks can delete by GUID without a cursor, so returning the cursor alone cannot guarantee those paths are safe.

Blizzard uses `C_Item.LockItem` and GUID unlocks for temporary auction and runeforge selections. BagMarks requests holds only during transfer or item-targeting contexts, independently of use-spell classification. It checks the exact location/GUID, skips preexisting busy/held items, records ownership before synchronous lock events, and confirms an acquired hold. Only recorded acquisitions are released when a context ends, the mark changes, protection is disabled, or the player logs out. Saved marks remain while ordinary use, equipping, sorting, and bank movement stay available. The client exposes no lock-owner token. If another addon acquires the same hold later, ownership cannot be perfectly distinguished. Simultaneous lock addons require testing and may conflict.

The release-verification patch pairs `LockItem(location)` with `UnlockItem(location)` when the current location resolves to the recorded GUID, as Blizzard's [auction item display](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_AuctionHouseUI/Shared/Blizzard_AuctionHouseSharedTemplates.lua) does. The pinned item API declares this method without a protected/combat restriction. Missing or thrown location unlocks fall back to `UnlockItemByGUID` for the owned GUID. A successful `pcall` is not an acknowledgement: the acquisition record remains until an exact readable location reports `IsLocked == false`. Delayed verification observes for up to two seconds without sending further unlock requests, then retains an unverified status and warns once. Later events can still confirm release. A new acquisition invalidates the old check token. Unreadable data never proves release, and a preexisting busy item is never acquired or unlocked. The busy flag also covers server item movement, so retaining the record does not prove an addon lock still exists. A release already forgotten by an earlier build cannot be safely reconstructed from an item ID or mark.

Transfer/targeting protection updates synchronously on context events. The pinned spell-book export declares `CURRENT_SPELL_CAST_CHANGED` synchronous. Either positive `SpellCanTargetItem()` or `SpellCanTargetItemID()` result applies a hold; if those are unavailable, a positive `SpellIsTargeting()` result is the fallback. Unknown optional targeting data does not freeze every Locked item. Ground targeting alone does not hold an item supplying its own spell. Merchant, mail, trade, and auction events acquire holds before deferred UI work. Closing the final risk releases owned holds for all item types. Banking alone is not a risk context. Direct or unreadable spell-targeting paths retain the documented protection limits.

Use-spell and consumable metadata are never required for ordinary gameplay. ## Automatic marked-junk sales

Automatic selling is an account-wide preference that starts off. Both sale paths read `C_Container.GetBackpackSellJunkDisabled()` for the backpack and `C_Container.GetBagSlotFlag(bag, Enum.BagSlotFlags.ExcludeJunkSell)` for equipped bags. A missing or unreadable flag excludes the bag from BagMarks sales. [Blizzard bag settings](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/ContainerFrame.lua)

EllesmereUI Bags 9.8.8 checks each slot's item ID and busy flag before selling. Its QoL module can also call the native bulk seller repeatedly. RestedXP Guides v4.11.36 picks up each selected slot and calls `PickupMerchantItem`. BagMarks leaves each seller's classification and settings under its control. If a queued Junk GUID is already missing or busy, BagMarks skips it and proceeds through its original selection. Replacing an item in the same slot cannot add it to that selection.

Only a transition into an open merchant schedules a sale. A short deferred start lets native merchant setup finish, then captures eligible carried Junk GUIDs. Later marks and inventory updates do not expand that selection or restart a stopped sale. Enabling the option at an already-open merchant takes effect on the next visit. A deliberate manual preview cancels the delayed automatic start; an existing BagMarks confirmation also prevents background selling.

Automatic and manual sales share eligibility and per-action revalidation of GUID, mark, count, and price. The merchant's Buy tab must be visible, the cursor empty, and item targeting and combat inactive. Queues wait for each result and stop on rejection or the existing two-second timeout. Turning the preference off cancels automatic work while leaving an explicitly confirmed manual sale alone. Merchant closure, combat, reset, disable, and logout invalidate queued callbacks. The automatic queue handles all captured eligible stacks; manual previews retain their 12-stack cap. The merchant's finite buyback capacity still applies.
