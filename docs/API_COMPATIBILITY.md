# Forever API compatibility and limitations

Audit date: **2026-11-14**. Target: **1.60.1**, TOC **16001**. Source baseline: the exported Blizzard UI and generated API definitions at [Gethe/wow-ui-source commit bebcb6bf309cf41b41bd74f8ca651e6a105b2676](https://github.com/Gethe/wow-ui-source/commit/bebcb6bf309cf41b41bd74f8ca651e6a105b2676), labelled **1.60.1 (70938)**. This mirror contains Blizzard's client source, rather than an addon author's inferred API list. The source was inspected before implementation. Presence in an export establishes API shape, not a successful runtime test.

```sh
python3 tools/audit_api.py /path/to/wow-ui-source
```

The addon checks required namespaces and method availability. It does not use an interface-number threshold to infer a Classic API. Missing item identity disables item features; missing optional menu or settings support does not substitute a legacy implementation. Unreadable or secret item data is ignored before comparison. Events are registered defensively for differing client revisions.

## Input, mail and collector compatibility in 1.1.0

Marking overlays register `AnyUp`, as used by Blizzard's compartment buttons, and pass through every unselected mouse button. The configured modifier combination must match exactly. Explicit None and Marking Mode only settings permit using a spare mouse button or a mode toggle instead of conflicting Ctrl/Shift shortcuts. Locked-item guards are independent of the chosen marking button. The source confirms these registration methods; native hit testing with every supported mouse button still needs a client pass.

The mail source above focuses the recipient field when Send Mail opens and clears it on `MAIL_SEND_SUCCESS`. BagMarks post-hooks the frame's show and field's text-change scripts, then defers its fill until Blizzard's handlers finish. User-originated edits inhibit filling for the current draft, including clearing the name. Replies and nonempty fields remain unchanged. The selected default name is highlighted when the field already has focus. An unfinished edit to the default in BagMarks settings is never used. Closing the mailbox invalidates pending work, and a successful send cancels any remaining attachment queue before preparing the next draft.

Ellesmere's minimap contract was inspected at commit `1a2b149c86777860618dcd85a254097d91602e11`, using the author's [button collector](https://github.com/EllesmereGaming/EllesmereUI/blob/1a2b149c86777860618dcd85a254097d91602e11/EllesmereUIMinimap/EUI_Minimap_Buttons.lua) and [flyout implementation](https://github.com/EllesmereGaming/EllesmereUI/blob/1a2b149c86777860618dcd85a254097d91602e11/EllesmereUIMinimap/EUI_Minimap_Flyout.lua). It discovers named minimap buttons, tracks addon-intended visibility, hides grouped buttons, and reparents/resizes them for its grid. BagMarks' old repeated `SetShown(true)` calls could revive an invisible hit target, and its drag callbacks could move a collected button back toward the group toggle. Parent checks alone also missed collector rows that retain Minimap parenting.

BagMarks now changes visibility only when the user's preference changes, recognizes foreign anchors/sizes, and keeps its drag timer on a separate frame. A transparent BagMarks button disables its own mouse hit target until visible again. No Ellesmere private table, shared button, menu, layout, or callback is modified. The stable button name and icon remain discoverable. Mock regressions cover closed collectors, reparented flyouts, rows with unchanged parents, collector-owned update scripts, and an independent AddOns compartment entry. Actual behavior with the user's installed Ellesmere version remains an in-game acceptance item.

## GUID behavior and stack policy

`GetItemGUID` identifies the physical item or stack exposed at an item location. Marks and snapshot metadata use GUID keys in per-character SavedVariables. No lookup uses an item ID to retrieve a mark. Item IDs are used only to identify potentially ambiguous stack changes and to verify an operation's captured item data.

The inspected APIs do not expose authoritative split/merge ancestry. Actual GUID stability during sort, split, merge, bank transfer, and outgoing attachment removal must be measured in Forever. The implementation therefore follows these rules:

- An ordinary move with the same GUID retains the same mark.
- Splitting keeps the source GUID's state; a new GUID starts Normal. There is no automatic mark inheritance.
- Merging keeps the surviving GUID's state, which may be Normal. A growing marked stack is excluded from helpers until reviewed. Possible recipients of a diminished marked stack are also flagged for review, without copying the source's state.
- Multiple possible recipients can receive a review flag. This may conservatively exclude extra stacks, but never silently marks identical copies Locked, Junk, or Mail.
- A review flag is cleared only by an explicit mark selection, including Clear Mark. The tooltip explains the required review. A menu selection deliberately marks the whole current stack.
- Snapshots are reconciled only over accessible bag IDs. Closed-bank observations and unavailable GUID marks are retained. Returning mail attachments can recover their original mark. Old GUID records may remain after sale or sending; they cannot affect a newly created GUID.
- Changes made while the addon is disabled, an inaccessible item changes GUID, or a stack loses its GUID entirely cannot be reconstructed reliably. Review those stacks manually. Settings reset intentionally does not erase marks.

## Scope of lock protection

| Action | Implemented behavior | Remaining limit |
| --- | --- | --- |
| BagMarks bulk sale or attachment | Requires the exact Junk/Mail state and a reviewed, readable, eligible GUID before each action. | Runtime API eligibility and server timing still need verification. |
| Merchant/mail item clicks | An independent overlay consumes risky clicks on Locked instances. Ordinary left drag works outside these contexts. | Items already on the cursor, unsupported frames, modified left-click split/pickup paths, and direct API calls can bypass it. |
| Native Sell All Junk | Its visible button is guarded while a Locked poor-quality carried item is readable. | Existing confirmation dialogs, other triggers and third-party sellers bypass that button. |
| Disenchanting | Bag click guards block item-targeting clicks on Locked slots. They also block beneficial targeting spells. | Macros, profession interfaces, gamepad actions, or direct spell/item APIs are not intercepted. There is a discovery/event timing window. |
| Destroying | Locked icon, tooltip warning and settings notice remain the out-of-combat warning mechanism. | Once picked up, an item's deletion cannot be safely vetoed by a secure post-hook. BagMarks never replaces destruction APIs or confirmation dialogs. |
| Combat | Item reads, overlays, guards, marking and automation suspend. Marking mode turns off; bindings cannot change. The unprotected settings window remains usable. | No combat-time item protection is claimed. |

`C_Item.LockItem`/`UnlockItem` and GUID variants are present. Blizzard uses these for temporary UI selection, for example in auction and runeforge frames. They are not documented as persistent protection, provide no addon-owned lock token, and can interfere with moving or equipping. BagMarks deliberately does not take or release these shared client locks. A post-hook runs after an action and cannot veto it; it is used only for visual refresh, never as a pretend sale/delete barrier.

Mail handling conservatively excludes bound and account-bound items even if a specific recipient would be eligible. The client remains the final authority for unique, duration, conjured, level, faction, and realm restrictions. Refused attachments are returned from the cursor picked up by that action, the queue stops, and the marks remain. A two-second acknowledgement timeout never retries a destructive operation automatically.

## Client verification still required

The mock does not model secure execution, forbidden frames, actual secret values, frame levels, mouse event propagation, native menu lifecycle, item GUID allocation, server acknowledgement, or Blizzard's binding-file loader. It cannot certify absence of taint. Verify those behaviors and the precise layout against the current Forever build using [TESTING.md](TESTING.md). Default combined and separate bags and Forever's bank panel are supported integration targets; replacement bag addons are not.
